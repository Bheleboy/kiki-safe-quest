# Architecture rules
- Homepage section exports live in a dedicated landing module and derive lesson/module/reward counts from existing course and armour data to prevent duplicated content drifting.
- Homepage actions use the shared Button with asChild for navigation; auth and cookie consent remain owned by the existing application shell.
- Non-home presentation uses scoped editorial styles and shared public-page framing so visual consistency does not alter homepage composition or application behavior.
- Serve brand font weights locally through global font-face declarations to keep typography reliable without remote stylesheet dependencies.
- Password sign-in goes through the `secure-login` edge function and every data table carries a RESTRICTIVE `require_registered_session` policy; sessions must be registered in `user_sessions` (device-bound) or they cannot read/write data, so direct auth-API sessions are useless.
- Security edge functions share helpers in `supabase/functions/_shared/security.ts`; security notices go through the platform app-email send function with fixed-copy templates restricted to service-role callers, because the auth queue only accepts auth-hook runs and free-form content would allow phishing.
- Signup, password reset and password change go through edge functions (`secure-signup`, `secure-reset-request` + `complete-password-reset`, `change-password`) that enforce the shared password policy; never call `supabase.auth.signUp`/`updateUser({password})` from the client.
- Parent-only routes are wrapped in `ParentGate` and parent-only actions on shared pages use `useParentPin().guard` (server-verified PIN, client-side unlock window); `InactivityGuard` handles idle sign-out per route group; sign-out always revokes the registered session server-side first.
- Accounts flagged in the server-only `security_flags` table (set by "This wasn't me" and admin sign-out, cleared by password reset) cannot sign in with their password; first-device auto-trust only applies when the user never had any trusted device row, revoked included, so revocation cannot be bypassed.
- Switching the active learner on a device (stored per device in localStorage) requires the parent PIN on both the family page and /course, so siblings cannot do each other's work by editing the URL.
- Admin stats exports verify SiteChecker sessions and client membership server-side before using local service-role RPC access, so the separate dashboard never needs this project's private key.
- Warrior Pass tables (app_settings, orders, entitlements, armour_kits, shipments, warrior_points, bulk codes) reference users via public.profiles, are written only by service-role edge functions, and paid access is decided solely by `public.has_course_access`, so client writes or book_purchases can never grant access.
- The Warrior Pass course gate lives in `useCourseAccess` as pure, tested helpers and fails open (loading, errors, missing or malformed settings mean full access), so a network or policy problem can never lock a child out.
- Warrior Pass payments: prices are computed only in `create-checkout` from app_settings, every checkout needs a fresh server-verified parent PIN (admins included), and only the signature-verified `yoco-webhook` fulfils orders via the service-role `fulfill_warrior_pass_order` RPC, so the browser return page can never unlock anything.
